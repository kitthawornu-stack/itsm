# ADR-002 — การจัดลำดับงานด้วย LexoRank

**สถานะ:** 🟡 ร่าง · **วันที่:** 2569-08-24 · **เจ้าของ:** Tech Lead

## บริบท

ผู้ใช้ลากจัดลำดับงานใน Backlog และ Board ตลอดเวลา Backlog จริงของทีมพัฒนามี
2,000–8,000 ใบ การลากหนึ่งครั้งต้องเร็วและต้องไม่ชนกันเมื่อคนสองคนลากพร้อมกัน

## ทางเลือกที่พิจารณา

| ทางเลือก | ผลของการลาก 1 ครั้ง |
|---|---|
| `position INT` เรียงต่อเนื่อง | UPDATE ทุกแถวที่อยู่หลังจุดแทรก — ลากขึ้นบนสุดของ backlog 5,000 ใบ = UPDATE 5,000 แถว |
| `position` แบบเว้นช่วง (100, 200, 300) | เร็วในช่วงแรก แต่ต้อง rebalance ทั้งคอลัมน์เมื่อช่องว่างหมด ซึ่งเกิดแน่นอน |
| **LexoRank** (สตริงเรียงลำดับได้) | UPDATE แถวเดียวเสมอ |

## การตัดสินใจ

ใช้ **LexoRank** — เก็บใน `work_item.rank VARCHAR(255)` แบบ base-36
โดยแบ่งเป็น 3 bucket (`0|`, `1|`, `2|`) เพื่อรองรับการ rebalance แบบไม่ล็อกทั้งตาราง

- ลำดับใหม่ = คำนวณค่ากึ่งกลางระหว่าง rank ของแถวบนและแถวล่าง
- ต้องมี unique index `(tenant_id, project_id, rank)` และจัดการ collision ด้วย retry
- Background job ตรวจความยาวของ rank — ถ้าเฉลี่ยเกิน 12 ตัวอักษร ให้ rebalance bucket

## ผลที่ตามมา

**ดี** — ลากหนึ่งครั้ง = UPDATE แถวเดียว · ทำงานถูกต้องแม้คนหลายคนลากพร้อมกัน · ไม่ต้อง lock ทั้งคอลัมน์

**ร้าย — และต้องรับมือ**
- อัลกอริทึมซับซ้อนกว่า integer มาก ต้องมี unit test ครอบคลุมกรณีขอบ
  (แทรกบนสุด · แทรกล่างสุด · แทรกระหว่างสอง rank ที่ติดกันจนไม่มีที่ว่าง)
- สตริงยาวขึ้นเรื่อย ๆ ถ้าแทรกจุดเดิมซ้ำ ๆ → ต้องมี rebalance job จริง ไม่ใช่แค่วางแผนไว้
- เรียงลำดับใน SQL ต้องใช้ collation แบบ binary (`utf8mb4_bin`) บนคอลัมน์นี้เท่านั้น
  ไม่งั้นการเปรียบเทียบสตริงจะไม่ตรงกับ logic ฝั่ง application

## ต้องพิสูจน์ก่อนยอมรับ

Spike D ในสัปดาห์ที่ 2 — สร้าง 5,000 แถว ลากสลับ 100 ครั้ง ยืนยันว่าเป็น UPDATE แถวเดียวจริงทุกครั้ง
และลำดับที่ได้ตรงกับที่คาดหวัง
