Part 00

หลักคิด 6 ข้อ ที่ตัดสินว่าระบบนี้จะสำเร็จหรือพัง

ก่อนเขียนโค้ดบรรทัดแรก ทีมต้องตกลง 6 ข้อนี้ให้ตรงกัน — ทุกข้อคือสาเหตุที่โครงการ ITSM ส่วนใหญ่บานปลาย และเป็นเหตุผลที่ Jira ยังยืนอยู่ได้หลังผ่านมา 20 ปี

01 · Single Work Item Model

Incident, Task, Story, Change คือ “ของสิ่งเดียวกัน”

ทั้งระบบมีตารางหลักแค่ตารางเดียวคือ work_item ความต่างของ Incident กับ User Story อยู่ที่ Issue Type + Workflow + Field Configuration ที่ผูกกับมัน ไม่ใช่ตารางคนละใบ นี่คือแก่นที่ทำให้ Jira ต่อยอดได้ไม่รู้จบ และทำให้เราลิงก์ “Incident → Problem → Change → Story” ข้ามโดเมนได้ในคิวรีเดียว

02 · Scheme over Hardcode

ทุกพฤติกรรมมาจากคอนฟิก ไม่ใช่ if-else ในโค้ด

Workflow Scheme, Field Scheme, Screen Scheme, Permission Scheme, Notification Scheme, SLA Policy — ทั้งหมดเป็นข้อมูลในฐานข้อมูลที่แอดมินแก้เองได้ ถ้าลูกค้าขอ “เพิ่มสถานะรออนุมัติ” แล้วต้อง deploy ใหม่ แปลว่าสถาปัตยกรรมผิดตั้งแต่ต้น

03 · Queue-first

คนใช้งานจริงอยู่กับ “รายการ” 90% ของเวลา

Agent ไม่ได้เปิดตั๋วทีละใบ เขาอยู่กับคิว กรอง จัดลำดับ แล้วลุยทีละ 20 ใบ ดังนั้น List View, Saved Filter, Bulk Action และ Keyboard Navigation คือฟีเจอร์ระดับ P0 ไม่ใช่ของแถมท้ายเฟส

04 · Audit by Default

ทุกการเปลี่ยนแปลงต้องตอบได้ว่า ใคร ทำอะไร เมื่อไหร่

work_item_history เขียนทุก field ที่เปลี่ยน ทุก transition ทุกการให้สิทธิ์ — เขียนแบบ append-only ในทรานแซกชันเดียวกับการแก้ข้อมูล ไม่ใช่ trigger แยก เพราะ ISO 27001 และ PDPA ต้องการหลักฐานนี้ และเพราะ MTTR วิเคราะห์ไม่ได้ถ้าไม่มี timeline

05 · API-first

หน้าเว็บของเราคือลูกค้ารายแรกของ API ตัวเอง

ไม่มี endpoint ลับที่หน้าเว็บเรียกได้คนเดียว ทุกอย่างผ่าน REST v1 ที่มี OpenAPI spec — บังคับให้ contract สะอาดตั้งแต่วันแรก และทำให้ Automation, Webhook, Mobile, และการ integrate กับระบบเดิมของลูกค้าเกิดขึ้นได้โดยไม่ต้องรื้อ

06 · Multi-tenant ตั้งแต่ตารางแรก

เติม tenant_id ทีหลัง = เขียนใหม่ทั้งระบบ

แม้เฟสแรกจะ deploy on-prem แบบ tenant เดียว แต่ทุกตารางมี tenant_id และทุกคิวรีผ่าน guard เดียวกันตั้งแต่วันแรก การเปิดโหมด SaaS ในเฟส 5 จึงเป็นการ “เปิดสวิตช์ + เพิ่ม billing” ไม่ใช่โปรเจกต์ใหม่

เส้นแบ่งขอบเขต — สิ่งที่เรา “ไม่ทำ” ใน v1.0

Marketplace/Plugin SDK แบบบุคคลที่สาม · Groovy/Script Runner ที่รันโค้ดผู้ใช้ · Confluence-class wiki เต็มรูปแบบ (เราทำ Knowledge Base ที่ผูกกับตั๋วเท่านั้น) · Portfolio/Advanced Roadmaps ข้ามหลายโปรเจกต์ · Mobile native app (ใช้ PWA ก่อน) — เขียนไว้ให้ชัดตั้งแต่วันนี้ เพื่อกันคำว่า “ให้เหมือน Jira ทุกอย่าง” กลับมาหลอกหลอนตอนเดือนที่ 9

อ่านก่อนใช้เอกสารนี้ขออนุมัติงบ

สิบสองส่วนถัดจากนี้ตอบว่า จะสร้างอย่างไร โดยสมมติว่าการตัดสินใจสร้างเกิดขึ้นแล้ว — Part 12 · Business Case ตอบคำถามที่มาก่อนหน้านั้นว่า ควรสร้างหรือไม่ ที่ขนาดองค์กร 10 agents ข้อสรุปไม่ตรงกับสมมติฐานของแผนนี้ ควรอ่าน Part 12 ก่อน

Part 01

สถาปัตยกรรมระบบ

Modular Monolith บน NestJS — ไม่ใช่ Microservices ตั้งแต่วันแรก ทีมขนาด 10 คนที่แตกเป็น 12 เซอร์วิสจะใช้เวลาครึ่งหนึ่งไปกับ infra แทนฟีเจอร์ เราวางขอบเขตโมดูลให้คมตั้งแต่ต้น เพื่อให้แยกออกได้ตอนที่มันคุ้มจริงเท่านั้น

Client

Next.js 15 · App Router

React 19 + TypeScript · Server Components สำหรับหน้าอ่านอย่างเดียว · Client Island สำหรับ Board/Editor · TanStack Query สำหรับ cache + optimistic update · Zustand สำหรับ UI state · dnd-kit สำหรับลากการ์ด · TanStack Virtual สำหรับคิว 10,000 แถว

API

NestJS 11 · Modular Monolith

REST v1 (OpenAPI auto-gen) + Socket.IO gateway · แบ่งเป็นโมดูลที่คุยกันผ่าน Application Service (วางแผนไว้ 16 · ของจริง 22) ไม่ใช่เรียก repository ข้ามโมดูล · CQRS แบบเบา (แยก command/query handler เฉพาะโดเมนที่ซับซ้อน)

Database

MySQL 8.0 · InnoDB · Prisma

Collation utf8mb4_0900_ai_ci · ใช้ CTE + Window Function สำหรับรายงาน · JSON column + Generated Column + index บน generated column แทน array/partial index ที่ MySQL ไม่มี · Read replica แยกสำหรับ reporting

Search

OpenSearch 2.x

บังคับใช้ตั้งแต่เฟส 0 — MySQL FULLTEXT ตัดคำไทยไม่ได้ ต้องใช้ ICU + Thai analyzer (dictionary-based) เป็นเป้าหมายของ HQL (ภาษาคิวรีแบบ JQL) ทั้งหมด

Cache & Queue

Redis 7 · BullMQ

Session/permission cache · SLA timer เป็น delayed job · Automation execution queue · Socket.IO adapter สำหรับ multi-instance · Rate limiting

Storage

MinIO (S3-compatible)

ไฟล์แนบ + รูปใน rich text · on-prem ใช้ MinIO ขึ้น SaaS สลับเป็น S3 ได้โดยไม่แก้โค้ด (S3 SDK เดียวกัน) · pre-signed URL + virus scan hook (ClamAV)

Identity

In-house (ตัดสินแล้วใน ADR-003)

ไม่ใช้ Keycloak และไม่มี SAML/OIDC/LDAP — ADR-003 ตัดสินไปแล้วว่าองค์กรนี้ไม่ได้ใช้ AD/LDAP ความคุ้มค่าของ Keycloak จึงหายไป · ใช้ session + bcrypt ของตัวเอง · แผนฉบับแรกเขียนไว้ก่อนได้คำตอบข้อนี้

Observability

OpenTelemetry Stack

Trace/Metric/Log ผ่าน OTel Collector → Grafana + Loki + Tempo + Prometheus · Sentry สำหรับ frontend error · ทุก request มี trace_id ที่โยงถึง audit log ได้

Delivery

Docker · Compose / K8s

On-prem ส่งเป็น Docker Compose bundle (ลูกค้าไทยส่วนใหญ่ไม่มี K8s) · SaaS รันบน K8s + Helm chart เดียวกัน · Prisma Migrate + gh-ost สำหรับตารางใหญ่

ขอบเขตโมดูลฝั่ง Backend — วางแผนไว้ 16 · ของจริง 22

project_id NOT NULL

1 · Workflow Engine — State Machine ที่เก็บในฐานข้อมูล

Transition หนึ่งเส้นประกอบด้วยสามชั้น: Condition (ใครเห็นปุ่มนี้) → Validator (กรอกครบไหมถึงจะผ่าน) → Post Function (ทำอะไรต่อหลังผ่าน) ทุกครั้งที่ผ่าน transition ระบบเขียน work_item_history และยิง event ในทรานแซกชันเดียวกัน

Admin · Workflow Editor — “ITSM: Incident Management v3”

สถานะสีเทา/ฟ้า/เขียวคือ category (TO DO / IN PROGRESS / DONE) — Board แม็ปคอลัมน์จาก category ส่วน Burndown นับ “เสร็จ” จาก category = DONE เท่านั้น สถานะเส้นประคือสถานะที่หยุดนาฬิกา SLA

2 · SLA Engine — จุดที่พังบ่อยที่สุดคือปฏิทินกับ timezone

โครงสร้าง

SLA Policy ผูกกับโปรเจกต์ → มีหลาย Goal ที่มีเงื่อนไข (HQL) + เป้าเวลา เช่น priority = P1 → 15 นาที ระบบไล่ goal จากบนลงล่าง ใช้ตัวแรกที่ match · แต่ละ Goal มี Start / Pause / Stop condition เป็นเงื่อนไขบนสถานะหรือฟิลด์

ปฏิทินทำการ

รองรับ 24×7, 8×5, และปฏิทินกำหนดเอง + วันหยุดราชการไทย (ต้องมีตารางวันหยุดที่อัปเดตรายปี รวมวันหยุดชดเชย) การคำนวณ “เหลืออีกกี่นาที” ต้องข้ามช่วงนอกเวลาทำการเสมอ

การคำนวณ

เก็บ elapsed_ms สะสม + started_at ของช่วงที่กำลังเดิน — คำนวณใหม่ทุกครั้งที่มี transition ไม่ใช่ทุกวินาที · นาฬิกาบนหน้าจอนับถอยหลังฝั่ง client จาก breach_at ที่เซิร์ฟเวอร์ส่งมา

การแจ้งเตือน

BullMQ delayed job ที่ 50% / 75% / 100% ของเป้า · เมื่อ transition ทุกครั้งต้อง ยกเลิก job เก่าแล้วตั้งใหม่ (ใช้ jobId ที่ deterministic) มิฉะนั้นจะได้เตือนซ้ำซ้อน

Test suite บังคับ

เอนจินนี้ต้องมีชุดทดสอบเฉพาะ ≥ 120 เคส ครอบคลุม: ตั๋วที่เปิดนอกเวลาทำการ · ตั๋วที่ pause คร่อมวันหยุดยาวสงกรานต์ · เปลี่ยน priority กลางทางแล้วเป้าเปลี่ยน · ตั๋วที่ reopen หลังปิดไปแล้ว · การเปลี่ยนปฏิทินย้อนหลัง · DST ของ tenant ต่างประเทศ ถ้าไม่มีชุดนี้ ตัวเลข SLA Compliance ในรายงานจะเชื่อถือไม่ได้ทั้งระบบ

3 · HQL — ภาษาคิวรีแบบเดียวกับ JQL

Lexer/Parser (Chevrotain) → AST → คอมไพล์เป็น OpenSearch DSL ภาษาเดียวนี้ถูกใช้ซ้ำใน 5 ที่: ช่องค้นหา, Saved Filter, Board Quick Filter, เงื่อนไขของ SLA Goal และ Condition ของ Automation — เขียนครั้งเดียวได้ประโยชน์ห้าเท่า

project = "SD" AND status IN ("Investigating", "Pending Customer") AND assignee = currentUser()
slaBreachIn < "2h" AND priority >= P2 ORDER BY slaBreachIn ASC
sprint IN openSprints() AND parent = "PLAT-14" AND statusCategory != Done
affectedCI IN downstreamOf("SRV-CORE-01") AND created >= startOfWeek()

ฟังก์ชันที่ต้องมีใน v1: currentUser() · membersOf() · now() · startOfDay/Week/Month() · openSprints() · closedSprints() · linkedIssues() · downstreamOf() · watchedByMe()

4 · Automation Engine — Trigger → Condition → Action

Automation · กฎ “ตั๋ว P1 ที่ไม่มีคนรับใน 10 นาที ให้ escalate”
⚡
Triggerเมื่อมีการสร้างงานใหม่ หรือฟิลด์ Priority ถูกแก้ฟัง event: work_item.created, work_item.field_changed(priority)
◈
Condition · HQLpriority = P1 AND assignee IS EMPTYประเมินซ้ำอีกครั้งตอนหน่วงเวลาครบ เพื่อกันกรณีมีคนรับไปแล้วระหว่างรอ
⏱
Delayรอ 10 นาที (ตามปฏิทินทำการ 24×7)BullMQ delayed job · jobId = rule:{id}:item:{id} เพื่อกันซ้ำ
▶
Action · 4 ขั้นมอบหมายให้หัวหน้าเวร → ตั้ง Escalation Level = 1 → แจ้ง LINE กลุ่ม IT-Oncall → คอมเมนต์บันทึกเหตุผลอัตโนมัติทุก action เขียน automation_run พร้อมผลลัพธ์และเวลาที่ใช้
Loop Protection

จำกัด 10 ครั้ง/กฎ/งาน/ชั่วโมง และตัดวงจรเมื่อ action ของกฎ A ไป trigger กฎ B ที่ trigger กฎ A ซ้ำ — ตรวจด้วย execution chain depth สูงสุด 5 ชั้น

Audit

ทุกการรันบันทึกใน automation_run: trigger ที่จุด, ผล condition, action ที่สำเร็จ/ล้มเหลว, เวลาที่ใช้ — แอดมินดูย้อนหลังได้ 90 วัน

Actor

การกระทำของ automation ใช้ system user ที่แยกชัดเจน แสดงในไทม์ไลน์ว่า “Automation · ชื่อกฎ” เพื่อไม่ให้ audit trail สับสนกับการกระทำของคน

สิ่งที่แผนนี้ประเมินผิดที่สุด ไม่ใช่ปริมาณโค้ด แต่เป็นสิ่งที่โค้ดซื้อไม่ได้ — Exit Criteria ของเฟส 1 ถึง 5 เกือบทั้งหมดวัดจาก การใช้งานจริง: ทีมย้ายมาใช้ · ตั๋วจริง 300 ใบ/เดือน · dogfooding · Change 10 ครั้งจริง · integration 3 ระบบ · tenant ทดลอง 3 ราย · ยังไม่มีข้อไหนเกิดขึ้นเลย และไม่มีข้อไหนที่เขียนโค้ดเพิ่มแล้วจะเกิดเอง

สิ่งที่แผนฉบับแรกเขียนไว้แล้วถูกยกเลิกภายหลัง: SSO (SAML/OIDC) และ LDAP/SCIM ถูกตัดออกตาม ADR-003 เพราะองค์กรไม่ได้ใช้ AD/LDAP · ย่อหน้าเดิมในเฟส 4 และ 5 ถูกแก้ให้ตรงแล้ว — แผนที่ยังสัญญาสิ่งที่ตัดไปแล้ว อันตรายกว่าแผนที่ไม่มีรายละเอียด เพราะมีคนวางแผนงานต่อจากมัน

มีของบางส่วนที่ทำไปพร้อมเฟสอื่น: การกั้นข้อมูลข้ามองค์กรพิสูจน์ได้ด้วย pnpm --filter @itsm/api verify:multitenant (ยกฐานชั่วคราว สร้างสององค์กร ตรวจ แล้วลบทิ้ง) · ชุดส่งมอบ on-prem ยกขึ้นจากภาพจริงและล็อกอินผ่านเบราว์เซอร์ได้แล้ว · นโยบายระยะเวลาเก็บข้อมูล (PDPA) มีแล้ว · ยังไม่มี: โหมด SaaS และ billing · การทดสอบเจาะระบบ · การซ้อมกู้คืนจาก backup · เครื่องมือย้ายข้อมูลจาก Jira

เกณฑ์ “p95 ของ API < 400 ms” วัดแล้ว และไม่ผ่าน — วัดบน build production ผู้ใช้พร้อมกัน 10 คน × 20 รอบ = 1,000 คำขอ · ล้ม 0 · p95 รวม 750 ms (วัดสองรอบได้ 782 และ 750 · รอบอุ่นเครื่องแยกออกแล้ว) · แยกรายเส้นทาง: สรุปรายงาน 394 ms ✓ · คิวงาน 440 ms · ค้นหา 496 ms · รายละเอียดงาน 761 ms และกระดาน 775 ms คือสองเส้นที่ถ่วงทั้งหมด · ข้อจำกัดของการวัด: เครื่องพัฒนาเครื่องเดียวที่รัน MySQL · OpenSearch · MinIO ใน Docker พร้อมกัน ไม่ใช่เครื่องเป้าหมาย — ตัวเลขจึงบอกว่า ต้องแก้ตรงไหน ได้ชัดกว่าบอกว่าผ่านหรือไม่ผ่านบนของจริง · สิ่งที่ยังอธิบายไม่ได้: โหมด dev เร็วกว่า production (p95 547 ms) ซึ่งกลับกับที่ควรเป็น · ยังไม่ได้ไล่หาสาเหตุ

ไล่ต่อจนเจอตัวแปรที่อธิบายได้: เวลาต่อคำขอแปรตาม จำนวนคิวรีต่อคำขอ เกือบเป็นเส้นตรง ที่ราว 13 ms ต่อคิวรี (MySQL อยู่ใน Docker บนวินโดวส์ ค่า round-trip ต่อคิวรีจึงแพง) — รายละเอียดงาน 58 คิวรี · กระดาน 39 · คิวงาน 20 · สรุปรายงาน 19 · วัดด้วย Com_select พร้อมกลุ่มควบคุม (ตอนไม่ยิงคำขอเลย มีแค่ 1–3 คิวรีต่อสองวินาทีจากงานเบื้องหลัง) จึงยืนยันว่าเป็นของคำขอจริง · ทางแก้ที่คุ้มที่สุดคือลดจำนวนคิวรี ไม่ใช่จูนคิวรีให้เร็วขึ้น · ผู้ต้องสงสัยอันดับแรก: permissionsFor() ยิง 3 คิวรีทุกครั้งที่ถูกเรียก และไม่มีแคชระดับคำขอ — แต่การแก้แตะโมดูลสิทธิ์ จึงต้องให้ Tech Lead อนุมัติก่อนตาม §4

ทดสอบทฤษฎีนั้นแล้ว และมันไม่จริง · เปิด previewFeatures = ["relationJoins"] ของ Prisma แล้ววัดใหม่ — มันลดคิวรีได้จริงทั้งระบบโดยไม่ต้องแก้โค้ดสักบรรทัด (การสั่ง relationLoadStrategy รายคิวรีไม่จำเป็น การสร้าง client ใหม่เปลี่ยนพฤติกรรมให้เอง): รายละเอียดงาน 52 → 38 คิวรี (−27%) · กระดาน 38 → 22 (−42%) · คิวงาน 19 → 13 (−32%) · สรุปรายงาน ไม่เปลี่ยน · วัดด้วยจำนวน Execute จาก general log ห้ารอบต่อเส้นทาง ค่าคงที่ทุกรอบ และมีกลุ่มควบคุม (/health = 2 คิวรี) · คำตอบเหมือนกันทุกไบต์ ทั้งสี่เส้นทางที่เทียบ (เทียบ JSON ทั้งก้อนหลังเรียงคีย์) · แต่เวลาแทบไม่ขยับ: p95 รวม 653 → 638 ms · กระดาน 665 → 627 · รายละเอียด 698 → 658 — ตัดคิวรีทิ้ง 42% ได้เวลาคืนมา 5.7%

ข้อสรุปที่ต้องแก้ในแผน: "เวลาต่อคำขอแปรตามจำนวนคิวรีเกือบเป็นเส้นตรงที่ 13 ms ต่อคิวรี" เป็นความสัมพันธ์ที่บังเอิญ ไม่ใช่เหตุ-ผล · Prisma ยิงคิวรีของ relation แบบขนาน การตัดคิวรีออกจึงไม่คืนเวลาเป็นเส้นตรง · ตัวเลข 13 ms มาจากการเทียบข้ามคนละเส้นทาง ซึ่งต่างกันทั้งจำนวนคิวรีและปริมาณข้อมูลที่ต้องประกอบ · การทดลองนี้เปลี่ยนตัวแปรเดียว บนเส้นทางเดิม จึงแยกสองอย่างนั้นออกจากกันได้เป็นครั้งแรก · ตัดสินแล้วว่าไม่เปิดใช้ — 15 ms ไม่คุ้มกับการพึ่ง preview feature ที่เปลี่ยน วิธีทำงานของทุกคิวรี · คำตอบเหมือนกันทุกไบต์ทั้งสี่เส้นทางที่เทียบ มันจึงเป็น ตัวเลือกที่เปิดได้ทันทีถ้าวันหนึ่งคุ้ม แต่วันนี้ไม่ใช่ และการวัดรอบต่อมา ก็ชี้ว่าคอขวดไม่ได้อยู่ที่จำนวนคิวรีตั้งแต่ต้น

ไล่ต่อจนเจอคอขวดจริงแล้ว — และมันไม่ใช่ทั้งคิวรีและฐานข้อมูล

1) ปริมาณงานตันที่ ~70 คำขอ/วินาที ตั้งแต่ 2 คนขึ้นไป · วัดที่ 1 · 2 · 5 · 10 คน ได้ 42 · 64 · 75 · 65 คำขอ/วินาที ขณะที่ p50 โตเป็นเส้นตรง 60 → 84 → 210 → 438 ms — เพิ่มคนแล้วได้แต่คิวยาวขึ้น ไม่ได้งานเพิ่ม · p95 ที่ 10 คนจึงเป็นเวลารอคิว ไม่ใช่ต้นทุนของคำขอ · คำขอเดี่ยวใช้เวลาแค่ 58 ms

2) เพดานนั้นคือ CPU ในโปรเซส API · ระหว่างยิงโหลด โปรเซส API กิน 2.86 คอร์ ขณะที่คอนเทนเนอร์ MySQL อยู่ที่ 3.4% · เครื่องมี 20 คอร์ จึงไม่ได้ตันที่เครื่อง แต่ตันที่ว่าโปรเซสเดียวใช้ได้เท่านี้

3) CPU ต่อคำขอแพงมาก และแปรตามสองอย่างพร้อมกัน — สรุปรายงาน 23 ms (15 คิวรี · 1.9 KB) · คิวงาน 39 ms (19 · 31 KB) · รายละเอียด 69 ms (52 · 7.4 KB) · กระดาน 97 ms (38 · 177 KB) · พอดีกับ ~1.2 ms ต่อคิวรี บวก ~0.4 ms ต่อ KB ของคำตอบ บวกค่าคงที่ ~5 ms · ซึ่งอธิบายได้ว่าทำไม relationJoins ถึงช่วยนิดเดียว: มันลดครึ่งเดียวของสมการ บนเส้นทางเดียว แล้วถูกเจือจางด้วยอีกสี่เส้นทางในการวัด

ข้อสรุปตอนนั้นคือ ทางแก้ที่คุ้มที่สุดคือรัน API มากกว่าหนึ่งโปรเซส — ทดสอบแล้วและไม่จริงเช่นกัน · ยก API สามโปรเซส (หนึ่งตัวเปิดตัวตั้งเวลา สองตัวตั้ง SCHEDULERS=off) หลัง nginx แล้ววัดที่ 30 คน: ปริมาณงาน 67 → 75 คำขอ/วินาที ดีขึ้นแค่ 12% ทั้งที่โปรเซสเพิ่มสามเท่า (p95 2,582 → 2,020 ms ยังห่างจากเกณฑ์ 400 ms มาก)

เพดาน ~72–75 คำขอ/วินาที เป็นของจริง และไม่มีอะไรที่วัดได้ตันเลยสักอย่าง: API สามโปรเซสรวมกันใช้ 4.34 คอร์จาก 20 · MySQL 0.5% · nginx 0.01% · ตัวยิงโหลด 0.32 คอร์ · และ MySQL รับ round-trip ได้ถึง 8,746 คิวรี/วินาที ผ่านทางเดินเดียวกัน ขณะที่ของจริงใช้แค่ ~2,800

ยืนยันว่าไม่ใช่ข้อจำกัดของตัวยิง ด้วยการยิงสองตัวพร้อมกันตัวละ 15 คน: ได้ 36 + 36 = 72 คำขอ/วินาที เท่าเดิมเป๊ะ — closed-loop ที่ผู้ใช้จำนวนคงที่ ให้ปริมาณงาน = จำนวนคน ÷ เวลาตอบ จึงต้องแยกให้ออกว่าเพดานเป็นของระบบหรือของเครื่องมือ

ที่เหลืออยู่คือทางเดินข้อมูลผ่าน Docker Desktop บนวินโดวส์ ซึ่งวัดแยก ด้วย SELECT 1 ไม่เจอ เพราะต้นทุนน่าจะไปกับ ปริมาณไบต์ ไม่ใช่จำนวนคิวรี (กระดานตอบ 177 KB ต่อคำขอ) · ยังไม่ได้พิสูจน์ · และถ้าใช่จริง มันเป็นข้อจำกัดของเครื่องที่ใช้วัด ไม่ใช่ของระบบ — แปลว่าเกณฑ์ p95 ตอบไม่ได้บนเครื่องนี้ ต้องวัดบนโฮสต์ที่ใกล้ของจริง

สิ่งที่เลิกสงสัยได้แล้ว: MySQL · จำนวนคิวรี · permissionsFor() · จำนวนโปรเซสของ API · และตัวยิงโหลด — ทั้งห้าอย่างวัดแล้วว่าไม่ใช่คอขวด

7.3 · ธีมสว่างและมืด

Agent นั่งหน้าจอนี้ 8 ชั่วโมงต่อวัน และจอ Wallboard ของห้อง NOC มักอยู่ในห้องที่ปิดไฟ — ธีมมืดจึงไม่ใช่ของแถมเพื่อความสวย แต่เป็นข้อกำหนดด้านการใช้งาน รองรับทั้งสองธีมตั้งแต่ Phase 0 เพราะการเติมธีมมืดทีหลังหมายถึงการรื้อทุกคอมโพเนนต์ที่เคยเขียนสีตรง ๆ ลงไป

กฎข้อเดียวที่ต้องบังคับด้วย lint ตั้งแต่ commit แรก

ห้ามเขียนค่าสีลงในคอมโพเนนต์โดยตรง — ไม่มีข้อยกเว้น ทั้ง hex, rgb(), ชื่อสีของ Tailwind (bg-red-500) และ currentColor ที่สืบทอดมาจากที่ไม่ชัดเจน คอมโพเนนต์อ้างได้เฉพาะ semantic token เท่านั้น ตั้ง ESLint + Stylelint rule ที่ทำให้ CI แดงเมื่อเจอค่าสีดิบในโฟลเดอร์ packages/ui ถ้าไม่บังคับด้วยเครื่องมือ จะมีสีดิบหลุดเข้ามาเสมอ และธีมมืดจะพังเป็นจุด ๆ ที่หาไม่เจอ

สังเกตว่าลำดับความสำคัญของสายตายังเหมือนกันทั้งสองธีม — แถวที่ SLA ใกล้หลุดยังเด่นที่สุด และแถวที่เสร็จแล้วยังจมที่สุด นี่คือเกณฑ์ผ่านของธีมมืด ไม่ใช่ความสวยงาม

การเลือกธีมและการเก็บค่า

สามสถานะ ไม่ใช่สองสถานะ
  • ตามระบบ (ค่าเริ่มต้น) — ไม่ใส่ attribute ใด ใช้ @media (prefers-color-scheme: dark) ตัดสิน ผู้ใช้ส่วนใหญ่จะอยู่ในสถานะนี้และไม่เคยแตะสวิตช์
  • สว่างเสมอ — data-theme="light" บน root ต้องชนะแม้ระบบตั้งเป็นมืด
  • มืดเสมอ — data-theme="dark" ต้องชนะแม้ระบบตั้งเป็นสว่าง
  • เก็บค่าใน user preference บนเซิร์ฟเวอร์ ไม่ใช่ localStorage อย่างเดียว — Agent ที่สลับระหว่างเครื่องที่ทำงานกับโน้ตบุ๊กต้องได้ธีมเดิม · localStorage เป็นเพียงแคชเพื่อกันจอกระพริบ
กันจอกระพริบตอนโหลด (FOUC)
  • Next.js render ฝั่งเซิร์ฟเวอร์ ไม่รู้ธีมของผู้ใช้ ถ้าปล่อยให้ React ตั้งธีมหลัง hydrate ผู้ใช้ธีมมืดจะเห็นจอขาววาบหนึ่งเฟรมทุกครั้งที่โหลดหน้า
  • แก้ด้วย inline script ขนาดเล็กใน <head> ที่อ่านค่าจาก cookie แล้วเซ็ต data-theme บน <html> ก่อน CSS จะถูก apply — ใช้ cookie ไม่ใช่ localStorage เพราะเซิร์ฟเวอร์อ่าน cookie ได้ด้วย
  • ตั้ง CSS color-scheme: light dark เพื่อให้ scrollbar, dropdown ของ select และ form control ที่เบราว์เซอร์วาดเอง เปลี่ยนตามธีมด้วย — จุดนี้ถูกลืมบ่อยที่สุดและเห็นชัดที่สุด
  • ห้าม render โครงสร้าง DOM ต่างกันตามธีม ฝั่งเซิร์ฟเวอร์ ธีมต้องเป็นเรื่องของ CSS ล้วน มิฉะนั้นจะเกิด hydration mismatch

หกจุดที่ธีมมืดพังเป็นประจำในระบบแบบนี้

01 · กราฟและแผนภูมิ

ต้องมี palette คนละชุดต่อธีม สีที่แยกออกจากกันได้บนพื้นขาวอาจกลืนกันบนพื้นมืด · เส้นกริดและป้ายแกนต้องใช้ --border และ --text-faint ไม่ใช่สีเทาที่เขียนตายตัว

02 · รูปที่ผู้ใช้อัปโหลด

Screenshot ส่วนใหญ่เป็นพื้นขาว จะแสบตามากในธีมมืด · ใส่พื้นหลังกลางและเส้นขอบให้รูปทุกใบ พร้อมลดความสว่างเล็กน้อยจนกว่าผู้ใช้จะคลิกเพื่อดูเต็ม

03 · Rich text ที่มีสีฝังมา

ผู้ใช้วางข้อความจาก Word หรือตั้งสีตัวอักษรเองไว้ — ต้อง sanitize สีที่ contrast ไม่ผ่าน หรือแสดงบล็อกนั้นบนพื้นผิวกลางที่อ่านได้ทั้งสองธีม

04 · อีเมลแจ้งเตือน

โปรแกรมอ่านอีเมลคุมธีมเอง เราคุมไม่ได้ · ออกแบบเทมเพลตอีเมลเป็นธีมสว่างเสมอ และทดสอบว่ายังอ่านได้เมื่อ Gmail หรือ Outlook บังคับกลับสีเอง

05 · PDF และการพิมพ์

ส่งออกเป็นธีมสว่างเสมอไม่ว่าผู้ใช้ตั้งอะไร · ต้องมี @media print ที่บังคับ token ชุดสว่าง ไม่งั้นผู้ใช้ธีมมืดจะได้ PDF พื้นดำที่กินหมึกทั้งตลับ

06 · โหมด Wallboard

จอ NOC บังคับธีมมืดเสมอ ไม่สนค่าที่ผู้ใช้ตั้งไว้ · และต้องเพิ่มขนาดตัวอักษรกับ contrast ขึ้นอีกขั้น เพราะคนดูจากระยะ 3–5 เมตร ไม่ใช่ 50 เซนติเมตร

การทดสอบธีมที่ต้องอยู่ใน CI

1) Visual regression บน 20 หน้าจอหลัก × 2 ธีม = 40 ภาพอ้างอิง · 2) axe-core ตรวจ contrast ทั้งสองธีม ไม่ใช่ธีมเดียว — นี่คือจุดที่ทีมส่วนใหญ่ตรวจแค่ธีมสว่างแล้วปล่อยธีมมืดหลุด · 3) Stylelint rule ที่ห้ามค่าสีดิบใน packages/ui · 4) ทดสอบสถานะ “ตามระบบ” จริง ๆ ด้วยการจำลอง prefers-color-scheme ทั้งสองค่า ไม่ใช่ทดสอบแค่สองสถานะที่กดเลือกเอง · 5) Storybook ต้องมีสวิตช์ธีมและทุก story ต้องดูได้ทั้งสองธีม

PDPA และการกำกับดูแลข้อมูล

  • คำขอของเจ้าของข้อมูล — ส่งออกและลบข้อมูลของบุคคลได้จริง รวมถึงในคอมเมนต์ ไฟล์แนบ และ audit log (ใช้การ pseudonymise แทนการลบใน audit เพื่อรักษาความครบถ้วนของหลักฐาน)
  • นโยบายเก็บรักษา — ตั้งอายุข้อมูลต่อประเภทได้ · ลบอัตโนมัติเมื่อครบกำหนด · มีบันทึกการลบ
  • เข้ารหัส — TLS 1.3 ระหว่างทาง · เข้ารหัสที่พัก (InnoDB tablespace encryption + MinIO SSE)
  • แยกข้อมูลระหว่าง tenant — ทดสอบอัตโนมัติที่พยายามอ่านข้ามtenant ต้องล้มเหลวเสมอ เป็นส่วนหนึ่งของ CI
  • ที่ตั้งข้อมูล: on-prem อยู่ในองค์กร · SaaS อยู่ในศูนย์ข้อมูลในประเทศไทย
กลยุทธ์การทดสอบ
  • Unit ≥ 70% บนโมดูลแกน · เอนจินทั้ง 4 ตัวต้อง ≥ 90%
  • Integration — Workflow, SLA, Permission, Automation ทดสอบกับฐานข้อมูลจริงใน Testcontainers ไม่ใช่ mock
  • E2E (Playwright) — 25 เส้นทางวิกฤต เช่น แจ้งตั๋วจาก portal → agent รับ → แก้ → ปิด → ให้คะแนน
  • Visual regression บน 20 หน้าจอหลัก ทั้งธีมสว่างและมืด
  • Accessibility — axe-core ใน CI ทุกหน้า + ทดสอบมือด้วย screen reader ทุกสิ้นเฟส
  • Load (k6) ทุกสิ้น sprint บนสภาพแวดล้อม staging ที่มีข้อมูลจำลอง 1 ล้านแถว
การส่งมอบและการดำเนินงาน
  • On-prem — Docker Compose bundle + สคริปต์ติดตั้ง + ตัวตรวจความพร้อมของเครื่อง (ลูกค้าไทยส่วนใหญ่ยังไม่มี Kubernetes)
  • SaaS — Helm chart เดียวกัน · blue-green deploy · migration รันแยกจาก rollout
  • Migration — Prisma Migrate สำหรับตารางทั่วไป · gh-ost บังคับใช้กับตารางเกิน 1 ล้านแถว · ทุก migration ต้องย้อนกลับได้

  • Observability — OpenTelemetry ครบ trace/metric/log · dashboard ของระบบตัวเองพร้อม alert บน error rate, queue depth, SLA job lag
  • Feature flag ทุกฟีเจอร์ใหญ่ เพื่อให้ deploy กับ release แยกจากกันได้

ทะเบียนความเสี่ยง

เรียงตามผลคูณของโอกาสและผลกระทบ — ทบทวนทุกสิ้นเดือน เจ้าของความเสี่ยงต้องรายงานสถานะการลดความเสี่ยง ไม่ใช่แค่ยืนยันว่ายังมีอยู่

ความเสี่ยงระดับทำไมถึงน่ากลัววิธีลดความเสี่ยงเจ้าของ
ขอบเขตบานปลายจากคำว่า “ให้เหมือน Jira” สูงมาก Jira มีฟีเจอร์สะสม 20 ปี การเทียบทีละอย่างจะไม่มีวันจบ และทีมจะรู้สึกว่าทำเท่าไรก็ไม่พอ เอกสาร Jira Parity Checklist ที่ลงนามร่วมกันตั้งแต่เฟส 0 · คำขอใหม่ต้องแลกออกจากขอบเขตเดิมเสมอ · ทบทวนขอบเขตอย่างเป็นทางการทุกสิ้นเฟสเท่านั้น PO
เอนจิน Workflow/Field Scheme ซับซ้อนเกินที่ประเมิน สูงมาก นี่คือหัวใจที่ทุกโมดูลพึ่งพา ถ้าออกแบบผิดจะรู้ตัวตอนเฟส 3 ซึ่งแก้ไม่ทันแล้ว Spike แบบมีเวลาจำกัด 3 สัปดาห์ในเฟส 0 ที่ต้องสร้าง workflow จริงได้จาก UI · รีวิวสถาปัตยกรรมโดยคนนอกทีม · เขียน ADR ให้ครบก่อนลงมือ Tech Lead
สมรรถนะของ Board และ Backlog ที่ข้อมูลจริง สูง ต้นแบบที่มี 20 การ์ดสวยงามเสมอ ปัญหาโผล่ตอนมี 2,000 ใบ ซึ่งคือตอนที่ลูกค้าใช้จริงแล้ว ใช้ virtualization ตั้งแต่บรรทัดแรก ไม่ใช่ optimize ทีหลัง · ทดสอบด้วยชุดข้อมูลจำลอง 1 ล้านแถวตั้งแต่เฟส 2 · ตั้ง performance budget ที่ทำให้ CI แดงถ้าเกิน FE Lead
การคำนวณ SLA ผิดเพราะปฏิทินและ timezone สูง ถ้าตัวเลข SLA ผิด รายงานทั้งระบบเชื่อถือไม่ได้ และความน่าเชื่อถือของโครงการจะพังทันที ชุดทดสอบเฉพาะ ≥ 120 เคส · สุ่มตรวจเทียบกับการคำนวณมือ 20 เคส/เดือนในช่วง pilot · เก็บ timestamp เป็น UTC เสมอ แปลงที่ชั้นแสดงผลเท่านั้น BE Lead
ค้นหาภาษาไทยไม่แม่น กลาง–สูง ภาษาไทยไม่มีช่องว่างระหว่างคำ ถ้าตัดคำผิด ผู้ใช้จะค้นไม่เจอและเลิกใช้ระบบค้นหาไปเลย บังคับใช้ OpenSearch + Thai analyzer ตั้งแต่เฟส 0 ไม่มี MySQL fallback · มีชุดคำค้นทดสอบภาษาไทย 200 คำที่ต้องผ่าน · เก็บ log คำค้นที่ไม่เจอผลลัพธ์มาปรับ dictionary BE Lead
ผู้ใช้ต่อต้านการเปลี่ยนระบบ กลาง–สูง ระบบที่ดีที่สุดก็ล้มเหลวได้ถ้าไม่มีคนใช้ — โดยเฉพาะกับทีมที่คุ้นกับระบบเดิมมานาน ดึงผู้ใช้จริง 5 คนเข้าร่วมตั้งแต่เฟส 0 เป็น champion · demo ทุกสิ้น sprint · pilot ที่เดือนที่ 5 ไม่ใช่รอจนจบ · ฝึกอบรม + มีคู่มือภาษาไทยก่อนเปิดใช้จริง PO
ทีมสูญเสียคนสำคัญ (bus factor = 1) กลาง ทีม 6 คนกับระบบขนาดนี้ หมายความว่าหลายโมดูลมีคนเข้าใจจริงแค่คนเดียว — และในโมเดล AI-first ความเสี่ยงนี้ซ้อนกับความเสี่ยง “ไม่มีใครเข้าใจโค้ดเลย” ด้านล่าง Pair programming บนโมดูลแกน · ADR + เอกสารสถาปัตยกรรมที่อัปเดตจริง · สลับคนดูแลโมดูลทุกสิ้นเฟส · ห้าม “เจ้าของโมดูล” แบบผูกขาด Tech Lead
ปรับ MySQL ให้รองรับ multi-tenant ตอนหลัง กลาง ถ้าลืม tenant_id แม้ตารางเดียว การเปิด SaaS จะกลายเป็นการเขียนใหม่ ใส่ tenant_id ทุกตารางตั้งแต่ตารางแรก · Prisma extension ที่บังคับ scope · ทดสอบข้าม tenant ที่ต้องล้มเหลวเสมอใน CI · ตรวจ migration ทุกใบว่ามีคอลัมน์นี้ Tech Lead
ประเมินงาน migration จากระบบเดิมต่ำเกินไป กลาง–ต่ำ ข้อมูลจริงของลูกค้ามักสกปรกกว่าที่คิด และการย้ายไม่ครบทำให้ go-live ล่ม ทดลองย้ายข้อมูลจริงตั้งแต่เฟส 2 ไม่ใช่เฟส 5 · มีรายงานตรวจสอบความครบถ้วนที่เทียบจำนวนและค่าสำคัญทีละรายการ · ยอมรับได้ว่าบางฟิลด์ย้ายไม่ได้ แต่ต้องบอกล่วงหน้า BE Lead
ทีมรีวิวโค้ดไม่ทันอัตราที่ AI ผลิต สูงมาก คอขวดใหม่ของโครงการ — เมื่อการเขียนเร็วขึ้น 3 เท่าแต่การรีวิวเร็วเท่าเดิม ส่วนเกินจะกลายเป็นโค้ดที่ merge ไปโดยไม่มีใครเข้าใจ และจะระเบิดตอนเดือนที่ 7 เพดาน 400 บรรทัดต่อ PR บังคับโดย CI · ห้าม merge สิ่งที่ผู้รีวิวอธิบายไม่ได้ · เมื่อรีวิวไม่ทัน ให้ลดอัตราการผลิต ไม่ใช่ลดมาตรฐาน · ผู้รีวิวต้องไม่ใช่คนที่สั่ง AI เขียนโค้ดนั้น Tech Lead
Invariant หลุดเงียบ ๆ ในโค้ดที่ AI เขียน สูงมาก AI เก่งเรื่อง happy path และอ่อนเรื่องกฎที่ต้องจำข้ามไฟล์ — tenant_id ที่หายไปหนึ่งคิวรีคือข้อมูลรั่วข้ามองค์กร และไม่มีเทสต์ปกติตัวไหนจับได้ บังคับด้วยสถาปัตยกรรมเท่านั้น ไม่ใช่วินัย — Prisma extension ที่ inject tenant scope ให้อัตโนมัติ · base service ที่เขียน audit ให้เอง · serializer กลางตัวเดียวสำหรับ field permission · ชุดทดสอบข้าม tenant ที่ต้องล้มเหลวเสมอ รันทุก PR Tech Lead
เอนจิน 4 ตัวถูกประเมินว่า AI จะช่วยได้มากกว่าความจริง สูง Workflow, SLA, HQL, LexoRank คือประเภทงานที่ AI ช่วยได้น้อยที่สุด (1.2–1.5×) แต่เป็นแกนกลางของทั้งระบบ ถ้าคิดว่าจะได้ 5× เหมือนงาน CRUD ไทม์ไลน์ 10 เดือนจะพลาดตั้งแต่เฟส 0 ประเมินเวลาสำหรับสี่ตัวนี้เท่าเดิมกับแผน 15 เดือน ไม่ลด · เขียนชุดทดสอบเป็นข้อกำหนดก่อนให้ AI ลงมือ · Tech Lead ทำเองด้วยมือในส่วนที่เป็นตรรกะหลัก Tech Lead

สัปดาห์ที่ 1 · ตัดสินใจและวางโครง
  • ตั้ง monorepo (Turborepo) — apps/web, apps/api, packages/ui, packages/hql, packages/types

  • ทำ ERD ของ 15 ตารางแกน แล้วรีวิวร่วมกันทั้งทีม
  • ตั้ง Docker Compose สำหรับ dev: MySQL 8 + Redis + OpenSearch + MinIO
  • ตั้ง CI: lint, typecheck, test, build container
  • Designer เริ่มไฟล์ token และคอมโพเนนต์ 8 ตัวแรกใน Figma + Storybook
  • PO เขียน Jira Parity Checklist ฉบับร่างให้ทีมค้าน
สัปดาห์ที่ 2 · พิสูจน์สมมติฐานที่เสี่ยงที่สุด
  • Spike A — Workflow Engine: สร้าง workflow 5 สถานะจาก UI แล้วให้ work item เดินตามได้จริง
  • Spike B — Custom Field EAV: สร้างฟิลด์ 3 ชนิด แสดงในฟอร์ม บันทึก และค้นหาได้
  • Spike C — OpenSearch + Thai analyzer: ค้นคำไทย 200 คำแล้ววัดความแม่น
  • Spike D — LexoRank: สร้าง 5,000 แถว ลากสลับ 100 ครั้ง ตรวจว่าเป็น UPDATE แถวเดียวจริง
  • สร้าง seed data ที่สมจริง 10,000 work item ไว้ใช้ตลอดโครงการ
  • สัมภาษณ์ผู้ใช้จริง 5 คน (agent 3 · ผู้ใช้ทั่วไป 2) บันทึกงานที่เขาทำจริงในหนึ่งวัน
  • ปิดท้ายด้วยการรีวิว: ถ้า spike ไหนไม่ผ่าน ให้ปรับแผนเฟส 0 ทันที ไม่ใช่รอ
คำถามที่ต้องมีคำตอบก่อนสิ้นสัปดาห์ที่ 2

1) ลูกค้ารายแรกคือใคร และเขามีตั๋วเดือนละกี่ใบ · 2) ต้องย้ายข้อมูลจากระบบเดิมหรือไม่ ระบบอะไร มีข้อมูลเท่าไร · 3) องค์กรใช้ AD/LDAP อยู่แล้วหรือไม่ — ตอบแล้วสำหรับลูกค้ารายแรก: ไม่ใช้ จึงตัด SSO/LDAP ออกตาม ADR-003 · ถ้ารายถัดไปตอบว่าใช้ ต้องเปิด ADR-003 ใหม่ · 4) มีข้อกำหนดด้าน compliance อะไรบ้าง (ISO 27001, PDPA, กฎเกณฑ์เฉพาะอุตสาหกรรม) · 5) ใครคือผู้มีอำนาจตัดสินใจตัดขอบเขตเมื่อเวลาไม่พอ — ข้อนี้สำคัญที่สุดและมักไม่มีใครถามจนสายเกินไป

13.2 · ทำไมเอนจินทั้งสี่ตัวคือจุดอ่อนที่สุด

SLA Engine

HQL Compiler

บั๊กไม่โผล่ที่การลากครั้งที่ 5 แต่โผล่ที่ครั้งที่ 500 เมื่อสตริงยาวจนแทรกตรงกลางไม่ได้ · เป็นความผิดพลาดที่การทดสอบด้วยมือไม่มีวันเจอ ต้องมีเทสต์ที่จำลองการลากหลายพันครั้ง

Workflow Engine

State machine ที่มี condition, validator และ post-function ผูกกันเป็นชั้น ๆ ความผิดพลาดปรากฏเป็น “ปุ่มที่ไม่ควรเห็นแต่เห็น” ซึ่งคือช่องโหว่ด้านสิทธิ์ ไม่ใช่บั๊กด้านการใช้งาน

AI ผลิตได้      ≈ 5,000 บรรทัด/วัน
ส่วนเกิน = หนี้ ไม่ใช่ความเร็ว

เพดานจริงของโครงการนี้คือ 1,200 บรรทัดต่อวัน ไม่ใช่ความเร็วของ AI — วางแผนบนตัวเลขนี้

กติกาที่ทำให้เพดานนั้นใช้ได้จริง
  • PR ไม่เกิน 400 บรรทัด บังคับด้วย CI — AI ผลิต PR 2,000 บรรทัดได้ง่ายมาก แต่ไม่มีใครรีวิวได้จริง คนจะกด approve ทั้งที่ไม่ได้อ่าน
  • ผู้รีวิวต้องไม่ใช่คนที่สั่ง AI เขียนโค้ดชิ้นนั้น — คนที่กำกับ AI มีอคติเข้าข้างผลลัพธ์ของตัวเองสูงกว่าการเขียนเอง เพราะไม่ได้ลงแรงเขียน
  • อธิบายได้จึง merge ได้ — ผู้รีวิวต้องอธิบายได้ว่าโค้ดทำงานอย่างไรและทำไมถึงถูก ไม่ใช่แค่ “เทสต์ผ่าน”
  • เมื่อรีวิวไม่ทัน ให้ลดอัตราการผลิต ไม่ใช่ลดมาตรฐานการรีวิว — ข้อนี้จะถูกท้าทายในเดือนที่ 5 ตัดสินไว้ตั้งแต่วันนี้ว่าจะไม่ผ่อน
