# ADR-004 — Modular Monolith ไม่ใช่ Microservices

**สถานะ:** 🟡 ร่าง · **วันที่:** 2569-08-24 · **เจ้าของ:** Tech Lead

## บริบท

ระบบมี 16 โมดูลฝั่ง backend ทีมมี 9 คน ระยะเวลา 15 เดือน
คำถามคือจะแยกเป็นเซอร์วิสตั้งแต่ต้นหรือไม่

## การตัดสินใจ

**Modular Monolith** — deploy เป็น process เดียว (บวก worker process แยกสำหรับ BullMQ)
แต่มีขอบเขตโมดูลที่บังคับใช้จริงในโค้ด

**กติกาที่ต้องบังคับด้วยเครื่องมือ ไม่ใช่ด้วยวินัย:**

- ทุกโมดูลมี `index.ts` ที่ export เฉพาะ Application Service — ห้าม export repository, entity, หรือ Prisma client
- ใช้ ESLint rule (`import/no-restricted-paths`) ที่ทำให้ CI แดง เมื่อมีการ import ข้ามโมดูลนอกทาง `index.ts`
- โมดูลคุยกันผ่าน method call หรือ domain event เท่านั้น ห้ามคิวรีตารางของโมดูลอื่นตรง ๆ
- ห้าม JOIN ข้ามขอบเขตโมดูลใน SQL — ถ้าต้องการข้อมูลจากอีกโมดูล ให้เรียก service ของมัน

## เกณฑ์การแยกเป็นเซอร์วิส (ห้ามแยกก่อนถึงเกณฑ์)

แยกได้เมื่อ **อย่างน้อยสองข้อ** เป็นจริง:

1. โมดูลนั้นต้อง scale คนละอัตราจากที่เหลืออย่างชัดเจน (วัดจาก CPU/memory profile จริง)
2. การ deploy โมดูลนั้นบ่อยกว่าที่เหลือ 3 เท่าขึ้นไป
3. มีทีมแยกที่รับผิดชอบโมดูลนั้นเต็มเวลา
4. failure ของโมดูลนั้นไม่ควรทำให้ทั้งระบบล่ม และตอนนี้มันทำให้ล่มจริง

**ลำดับที่จะแยกก่อนถ้าถึงเวลา:** `search-index` → `automation` → `notification` → `reporting`
ทั้งสี่ตัวนี้เป็นงาน async ที่ scale คนละแบบ และออกแบบให้แยกง่ายอยู่แล้ว

## ผลที่ตามมา

**ดี** — ทรานแซกชันเดียวครอบคลุมการเปลี่ยนสถานะ + เขียน history + ยิง event ได้จริง ·
ทีม 9 คนใช้เวลากับฟีเจอร์แทน infra · debug ง่าย · deploy ง่ายทั้ง on-prem และ SaaS

**ร้าย — และต้องรับมือ**
- โมดูลอาจรั่วเข้าหากันได้ถ้าไม่บังคับ — **จึงต้องมี ESLint rule ตั้งแต่ commit แรก ไม่ใช่ทีหลัง**
- ต้อง restart ทั้งระบบตอน deploy → ใช้ blue-green บน SaaS และแจ้งหน้าต่างบำรุงรักษาบน on-prem
- ฐานข้อมูลเดียวกันทั้งหมด → ต้องระวังคิวรีหนักจากโมดูล reporting แย่งทรัพยากร
  (แก้ด้วย read replica แยกตั้งแต่เฟส 4)
