# ADR-001 — วิธีเก็บ Custom Field

**สถานะ:** 🟢 ยอมรับแล้ว — พิสูจน์ด้วย Spike B · **วันที่:** 2569-08-24 · **เจ้าของ:** Tech Lead

## บริบท

ระบบต้องให้แอดมินสร้างฟิลด์เองได้ไม่จำกัด (14 ชนิดฟิลด์) โดยไม่ต้อง deploy ใหม่
ฟิลด์เหล่านี้ต้อง **ค้นหาได้ · กรองได้ · เรียงได้ · แสดงในลิสต์ได้** และต้องทำงานบน
MySQL 8 ที่มีข้อจำกัดต่างจาก PostgreSQL

## ทางเลือกที่พิจารณา

| ทางเลือก | ข้อดี | ข้อเสียที่ทำให้ตกรอบ |
|---|---|---|
| **A · Dynamic Column** (ALTER TABLE ตอน runtime) | คิวรีตรงไปตรงมา index ง่าย | MySQL จำกัด 4,096 คอลัมน์/ตาราง · DDL บนตาราง 5 ล้านแถวล็อกนานมาก · migration ระหว่าง tenant ต่างกันจนคุมไม่ไหว |
| **B · JSON column อย่างเดียว** | ยืดหยุ่นสูงสุด schema เดียวจบ | MySQL index บน JSON ต้องผ่าน generated column ทีละฟิลด์ — ซึ่งกลับไปเจอปัญหา DDL เดิม · เรียงและเปรียบเทียบชนิดข้อมูลไม่น่าเชื่อถือ |
| **C · EAV ล้วน** | ยืดหยุ่น ไม่มี DDL | ลิสต์ 50 แถวที่มี 12 custom field = JOIN 12 ครั้ง หรือ pivot ที่ช้ามาก |
| **D · EAV + JSON snapshot** (เลือกข้อนี้) | ได้ทั้งความยืดหยุ่นและความเร็วในการอ่าน | ต้องดูแลความสอดคล้องของข้อมูลสองที่ |

## การตัดสินใจ

ใช้ **ทางเลือก D**

- **แหล่งความจริง** คือตาราง `work_item_field_value` (EAV) — มีคอลัมน์แยกตามชนิด
  (`value_text`, `value_number`, `value_date`, `value_ref_id`) เพื่อให้ index และเปรียบเทียบได้ถูกชนิด
- **สำเนาสำหรับอ่าน** คือคอลัมน์ `work_item.field_snapshot JSON` — เขียนพร้อมกันในทรานแซกชันเดียวกัน
  ใช้เรนเดอร์ลิสต์และการ์ดโดยไม่ต้อง JOIN
- **การค้นหาและกรอง** ทั้งหมดไปที่ **OpenSearch** ไม่ใช่ MySQL (ดู ADR-005)
  จึงไม่ต้องสร้าง index บน MySQL สำหรับ custom field เลย

## ผลที่ตามมา

**ดี**
- ไม่มี DDL ตอน runtime — เพิ่มฟิลด์คือการ INSERT แถวเดียวใน `field_definition`
- ลิสต์ 50 แถวใช้คิวรีเดียว ไม่มี JOIN เพิ่มตามจำนวนฟิลด์
- multi-tenant ที่แต่ละ tenant มีฟิลด์คนละชุดทำได้ทันที

**ร้าย — และต้องรับมือ**
- `field_snapshot` อาจไม่ตรงกับ EAV ถ้าเขียนพลาด → **ต้องมี job ตรวจสอบความสอดคล้องรายวัน**
  ที่รายงานความต่าง และมีคำสั่ง rebuild snapshot จาก EAV
- ห้ามอ่าน `field_snapshot` เพื่อนำไปเขียนต่อ — เขียนต้องผ่าน EAV เสมอ
  บังคับด้วยการไม่ expose snapshot ออกจาก repository layer

## ผลการพิสูจน์ (Spike B)

ทดสอบจริงกับ MySQL 8 ในคอนเทนเนอร์ · ชุดทดสอบ `apps/api/test/custom-field.spec.ts` (14 เคส ผ่านทั้งหมด)

**ตัวเลขที่ตัดสิน — อ่านลิสต์ 50 แถวที่มี 12 custom field:**

| วิธี | เวลาเฉลี่ย 5 รอบ |
|---|---|
| อ่านจาก `field_snapshot` (JSON) | **2.2 ms** |
| JOIN EAV แล้วประกอบกลับ | 16.1 ms |
| **ต่างกัน** | **7.4 เท่า** |

50 งานสร้างแถวใน EAV **650 แถว** — นี่คือสาเหตุที่ JOIN ช้า และเป็นเหตุผลที่ snapshot คุ้ม

เกณฑ์ที่ตั้งไว้ล่วงหน้าคือต้องเร็วกว่า **อย่างน้อย 1.5 เท่า** มิฉะนั้นความซับซ้อนของ
การดูแลข้อมูลสองที่ไม่คุ้ม — ผลจริงเกินเกณฑ์มาก จึงยอมรับ ADR นี้

**สิ่งที่ Spike B พบเพิ่มและต้องแก้ schema:**

unique เดิม `(work_item_id, field_id, value_ref_id)` ใช้กับฟิลด์หลายค่าที่เก็บเป็น
ข้อความไม่ได้ เพราะทุกแถวมี `value_ref_id = NULL` จึงชนกันเอง และไม่มีทางรักษาลำดับ
ที่ผู้ใช้เลือก → เพิ่มคอลัมน์ `position` และเปลี่ยน unique เป็น
`(work_item_id, field_id, position)` (migration `20260824132446_field_value_position`)

**ข้อกำหนดที่ยืนยันแล้วว่าทำงาน:**

- เก็บและอ่านครบ 14 ชนิดฟิลด์ ด้วยคอลัมน์ที่ถูกชนิด
- ตัวเลขเก็บในคอลัมน์ตัวเลขจริง → `ORDER BY` ได้ลำดับเลข (9 มาก่อน 42) ไม่ใช่ลำดับพจนานุกรม
- `0` และ `false` เก็บได้ ไม่ถูกมองว่าเป็นค่าว่าง
- ฟิลด์หลายค่ารักษาลำดับ และเขียนทับแทนการเพิ่มต่อท้าย
- snapshot ตรงกับ EAV ทันทีหลังเขียน (ทรานแซกชันเดียวกัน)
- **เขียนล้มกลางทาง → ทั้ง EAV และ snapshot ไม่เปลี่ยน**
- ตัวตรวจสอบความสอดคล้องจับ snapshot ที่เพี้ยนได้ และ `rebuildSnapshot` กู้คืนจาก EAV ได้
