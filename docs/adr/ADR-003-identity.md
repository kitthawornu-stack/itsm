# ADR-003 — Keycloak หรือ In-house Auth

**สถานะ:** 🟢 **ตัดสินแล้ว — In-house** · **วันที่ตัดสิน:** 2569-08-26 · **เจ้าของ:** Tech Lead

> ADR นี้บล็อก Phase 0 อยู่หลายสัปดาห์ เพราะรอคำตอบข้อเดียว
> ตอนนี้ได้คำตอบแล้ว: **องค์กรไม่ได้ใช้ AD/LDAP**

## บริบท

ต้องรองรับ SAML 2.0, OIDC, LDAP/AD sync, SCIM (เฟส 5) และ MFA
แต่โหมด on-prem ส่งมอบเป็น Docker Compose bundle ที่ลูกค้าไทยต้องติดตั้งเอง —
ทุก container ที่เพิ่มเข้าไปคือภาระที่ลูกค้าต้องดูแล

## ทางเลือก

### A · Keycloak

**ดี** — ได้ SAML/OIDC/LDAP/MFA/SCIM ครบตั้งแต่วันแรก · ผ่านการตรวจสอบความปลอดภัยมาแล้ว ·
ไม่ต้องเขียน token lifecycle เอง · admin console พร้อมใช้

**ร้าย** — เพิ่ม container + ฐานข้อมูลของตัวเองใน on-prem bundle · ทีมต้องเรียนรู้ Keycloak
(learning curve จริงประมาณ 2 สัปดาห์) · การ sync ผู้ใช้ระหว่าง Keycloak กับตาราง `user` ของเรา
เป็นงานที่ต้องดูแลตลอดไป · อัปเกรด Keycloak เป็น breaking change บ่อย

### B · In-house (JWT + LDAP connector + SAML library)

**ดี** — bundle เล็ก ควบคุมได้ 100% · ตาราง `user` เป็นแหล่งความจริงเดียว ไม่มีปัญหา sync ·
ทีมเข้าใจโค้ดทั้งหมด

**ร้าย** — ต้องเขียนเองและ **ต้องเขียนให้ถูก**: token rotation, refresh token reuse detection,
session revocation, password reset ที่ไม่รั่วข้อมูล, rate limiting, MFA · SAML SP เป็นจุดที่
ทำผิดแล้วเกิดช่องโหว่ร้ายแรงได้ง่ายมาก · ประเมิน 4–6 สัปดาห์ของ backend หนึ่งคน

---

## การตัดสิน

**เลือก B — In-house** ตามเกณฑ์ที่ ADR ฉบับนี้เขียนไว้เองตั้งแต่ต้นว่า
*"ถ้าลูกค้าไม่ใช้ AD/LDAP ความคุ้มค่าของ Keycloak ลดลงมาก"*

องค์กรยืนยันว่า **ไม่ต่อ AD และไม่ต่อ LDAP** ซึ่งลบเหตุผลหลักของ Keycloak ออกไปทั้งข้อ
สิ่งที่เหลือคือ container เพิ่มหนึ่งตัว ฐานข้อมูลเพิ่มหนึ่งชุด และงาน sync ที่ต้องดูแลตลอดไป
เพื่อแลกกับความสามารถที่ยังไม่มีใครขอใช้

### ขอบเขตที่ตัดสินพร้อมกัน — สิ่งที่ **จะไม่สร้าง**

การตัดสินนี้แคบกว่าตัวเลือก B เดิม เพราะ "ร้าย" ส่วนใหญ่ของ B มาจากสิ่งที่ตอนนี้ไม่ต้องการ:

| ไม่สร้าง | เหตุผล | เงื่อนไขที่ต้องกลับมาทบทวน |
|---|---|---|
| SAML SP | ไม่มี IdP ให้ต่อ และเป็นจุดที่เขียนผิดแล้วเกิดช่องโหว่ร้ายแรงที่สุด | ลูกค้ารายใดขอ SSO กับ IdP ที่มีอยู่ |
| OIDC client | เหตุผลเดียวกัน | เหมือนกัน |
| LDAP/AD connector | องค์กรยืนยันว่าไม่ใช้ | องค์กรติดตั้ง AD ภายหลัง |
| SCIM | ไม่มีต้นทางให้ provision | มี IdP แล้วต้องการ auto-provisioning |
| Refresh token rotation | ใช้ session ฝั่งเซิร์ฟเวอร์แทน JWT จึงไม่มี refresh token ให้หมุน | เปลี่ยนไปใช้ JWT |

**การไม่สร้าง SAML คือส่วนที่ลดความเสี่ยงมากที่สุดของการตัดสินนี้** — ไม่ใช่การประหยัดเวลา

### สิ่งที่จะสร้าง

- รหัสผ่าน + session ฝั่งเซิร์ฟเวอร์ (opaque token ใน httpOnly cookie)
  **ไม่ใช่ JWT** — JWT เพิกถอนไม่ได้ถ้าไม่มีบัญชีดำ ซึ่งเท่ากับมี session อยู่ดี
  แต่ซับซ้อนกว่าและตรวจสอบยากกว่า · ที่ผู้ใช้ไม่เกินร้อยคน การอ่านตาราง session
  หนึ่งครั้งต่อคำขอไม่ใช่ปัญหา และการปิดบัญชีให้ผลทันทีจริง
- จำกัดจำนวนครั้งที่ลองรหัสผ่านผิด
- MFA แบบ TOTP — **ภายหลัง** ไม่ใช่รอบนี้ แต่โครง session ต้องรองรับได้โดยไม่รื้อ

### เงื่อนไขที่ต้องทำ

- โมดูล `identity` ห่อทุกอย่าง — โค้ดส่วนอื่นเรียกผ่าน `index.ts` เท่านั้น
  เพื่อให้เปลี่ยนไปใช้ Keycloak ทีหลังได้โดยแตะที่เดียว (ADR-004)
- `dev-tenant.guard` ต้องถูกลบทิ้งเมื่อ identity พร้อม ไม่ใช่ปล่อยไว้เป็นทางลับ
- ทุกจุดที่แตะ auth ต้องมี Tech Lead อนุมัติ (CLAUDE.md §4)

## ผลที่ตามมา

**ปลดล็อก:** `identity` → `permission` → Workflow Editor → เกณฑ์ปิด Phase 0 ข้อสุดท้าย

**รับความเสี่ยงไว้:** การเขียน auth เองผิดพลาดได้ · ลดด้วยการจำกัดขอบเขต
(ไม่มี SAML/OIDC) และการเลือกกลไกที่ตรวจสอบง่ายที่สุดในทุกจุด
