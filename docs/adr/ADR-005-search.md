# ADR-005 — OpenSearch เป็นแหล่งค้นหาเดียว ไม่มี MySQL fallback

**สถานะ:** 🟡 ร่าง · **วันที่:** 2569-08-24 · **เจ้าของ:** BE Lead

## บริบท

เนื้อหาส่วนใหญ่ในระบบเป็นภาษาไทย ซึ่ง **ไม่มีช่องว่างระหว่างคำ**
MySQL `FULLTEXT` ตัดคำด้วยช่องว่างและเครื่องหมายวรรคตอน จึงมองประโยคภาษาไทยทั้งประโยค
เป็นคำเดียว — ค้นหาคำว่า "รหัสผ่าน" ในประโยค "ลืมรหัสผ่านเข้าระบบ" จะไม่เจอ

MySQL 8 มี ngram parser ที่พอใช้ได้บ้าง แต่ให้ผลลัพธ์ที่มี noise สูงมาก
และไม่รองรับ relevance scoring ที่ยอมรับได้

## การตัดสินใจ

**OpenSearch 2.x เป็นแหล่งค้นหาเดียว** — ทั้ง full-text และการกรอง/เรียงด้วย HQL
ไม่สร้าง code path สำรองที่คิวรี MySQL

- ใช้ `icu_tokenizer` + Thai dictionary-based analyzer สำหรับฟิลด์ข้อความ
- ทุกฟิลด์ที่กรองหรือเรียงได้ (รวม custom field ทุกตัว) ต้องอยู่ใน index
- HQL compiler แปลง AST → OpenSearch DSL โดยตรง ไม่มี SQL compiler
- ซิงก์ผ่าน `search-index` module ที่ฟัง domain event — ไม่ใช่ polling
- Multi-tenant: index alias ต่อ tenant บน SaaS · index เดียวบน on-prem

## ทำไมไม่มี fallback

ทางเลือกที่ปฏิเสธคือ "ใช้ OpenSearch ถ้ามี ไม่งั้นใช้ MySQL"
ปัญหาคือมันสร้าง code path สองชุดที่พฤติกรรมต่างกัน — ผลการค้นหาไม่เหมือนกัน
ระหว่างสองโหมด ทำให้ทดสอบไม่ครบและ debug ยาก
**OpenSearch จึงเป็น dependency บังคับของ on-prem bundle** เหมือน MySQL และ Redis

## ผลที่ตามมา

**ดี** — ค้นหาภาษาไทยแม่นจริง · HQL ซับซ้อนเท่าไรก็ทำงานเร็ว · aggregation สำหรับ dashboard ได้ฟรี ·
code path เดียว ทดสอบง่าย

**ร้าย — และต้องรับมือ**
- **on-prem bundle หนักขึ้นมาก** — OpenSearch กิน RAM อย่างน้อย 2 GB
  ต้องระบุความต้องการขั้นต่ำของเครื่องให้ชัดในเอกสารติดตั้ง และมีตัวตรวจความพร้อมก่อนติดตั้ง
- **ข้อมูลไม่สอดคล้องกันชั่วคราว** (eventual consistency) — ผู้ใช้แก้ตั๋วแล้วค้นหาทันทีอาจยังไม่เจอ
  → ใช้ `refresh_policy: wait_for` เฉพาะการเขียนที่ผู้ใช้ทำเอง และแสดงผลจาก MySQL ทันที
  สำหรับหน้า detail (ซึ่งไม่ผ่าน search อยู่แล้ว)
- **index หลุดหรือเสียหาย** → ต้องมีคำสั่ง full reindex ที่รันได้บน production
  พร้อมประมาณเวลา และทดสอบจริงตั้งแต่เฟส 1

## ต้องพิสูจน์ก่อนยอมรับ

Spike C ในสัปดาห์ที่ 2 — ชุดคำค้นภาษาไทย 200 คำที่ต้องผ่านเกณฑ์ความแม่นที่ตกลงกัน
พร้อมเปรียบเทียบผลกับ MySQL ngram เพื่อยืนยันว่าความต่างมีนัยสำคัญจริง
